## Backend — 82 tests

### `test_domain_extraction.py` — 14

Deterministic extraction and validation.

* Parses the verified `omnipod_discover_agp_summary_v1` layout: 12 fields, the correct
  mean (168 mg/dL), TIR (65.5 %), sensor coverage (88 %) and a 14-day period.
* Every extracted value keeps its printed label, page number and source line.
* `Goal: <4%` style lines are never read as values.
* All six consistency checks pass on the fixture; corrupting the printed GMI flips
  `gmi_mean` to failed, marks the field inconsistent and removes it from bulk confirmation.
* A missing value makes a check "not evaluable" (`passed is None`), never "passed".
* The unverified generic layout marks every field as requiring individual confirmation.
* Rejections, each with its Arabic message: wrong extension, empty file, truncated file,
  oversized file, a non-PDF with a `.pdf` name.
* A scanned (image-only) PDF is rejected with an explanation that OCR would be required.
* PyMuPDF reads the real fixture PDF and produces the same result as the text fixture.
* Unit conversion, rounding and number formatting.

### `test_api_reports.py` — 17

Upload, processing, history, corrections, isolation.

* Health and config endpoints; an unconfigured server returns explicit Arabic setup notes.
* Every patient route returns 401 without a token; an invalid token is rejected.
* Upload → background processing → `ready`, with the right format id, page count, 14 days,
  88 % coverage, `sufficient: true` and one of the four outcomes.
* Every extracted value exposes `source_label`, `source_page` and `source_text`.
* A PDF with no glucose metrics fails with an Arabic reason; a scanned PDF fails with the
  OCR explanation.
* Non-PDF → 422, truncated PDF → 422 `truncated`, oversized → 413.
* History lists the user's reports; **a second user receives 404 for another user's
  report**.
* A correction re-runs the checks and the analysis: `band_sum` flips to failed, the
  original extracted value is preserved alongside the correction, and the report returns
  to `needs_review`.
* Marking a value unavailable stores `null`, never `0`.
* An unknown metric key is rejected with 400.
* Without a Gemini key the summary is a local template and says why.

### `test_api_workflow.py` — 18

Follow-up state machine, reviewer authorisation, appointments, notifications.

* Create and submit; the shared snapshot carries the approved metrics.
* **Duplicate prevention**: a second open request for the same report → 409
  `duplicate_request`. Withdrawing the first frees the key.
* Invalid transitions rejected: re-submitting a submitted request, withdrawing one already
  under review, deciding before the review started.
* **A patient cannot reach the reviewer dashboard** (403); reviewer routes are not
  anonymous (401).
* The reviewer sees submitted requests **without `user_id`**, with the report's verified
  metrics and analysis attached.
* **Drafts are invisible to reviewers** — absent from the queue and 404 by id.
* Approval creates **exactly one** simulated appointment, flagged `is_simulated` and
  labelled as a prototype; every appointment the patient sees is simulated.
* Rejection (`data_completion`) creates **no** appointment and moves the request to
  `more_info_requested`, which can then be resubmitted.
* Notifications are generated by real events (`report_ready`, `followup_submitted`,
  `followup_decided`, `appointment_created`) and **reloading the list creates none**.
* Mark-one-read, mark-all-read, channel separation, per-channel delete.
* **A user cannot read another user's notification** (404).

### `test_api_screens.py` — 7

The data behind each screen.

* The ملفي payload exposes the Sukkar Plus service state and the reference targets for the
  selected profile; with no reports it reports zero rather than inventing one.
* الرئيسية reflects the real journey state before and after an upload.
* The Sukkar Plus landing has no fabricated metrics before an upload.
* The journey advances correctly through upload → follow-up → decision → appointment, and
  all five steps end complete.
* Appointments always carry the prototype note.
* جودة الحياة content carries sources and contains no dosing language.
* Changing the target profile changes the applied reference targets (TIR > 70 % → > 50 %).

### `test_analysis_and_ai.py` — 26

Rules, appointment preparation, Gemini guards.

* Values inside the reference targets → `routine_summary`; exceeding one →
  `review_suggested` naming the rule; the explanation states it is not a diagnosis.
* A 5-day period or 52 % coverage → `need_more_data`, never a reassuring result.
* An unspecified target profile does not invent targets.
* **Unverified values are never used by a rule.**
* The episode rule reports `not_applicable` for a printed summary rather than passing.
* The urgent-concern outcome is available without any reviewer and names emergency
  services.
* Every shipped rule is labelled `demonstration_only` and carries a source reference.
* Appointment preparation lists metrics with their sources, limitations and questions, and
  carries the disclaimer; with one report it **refuses** to compare and says why; with no
  report it names the gap.
* Comparison is refused for overlapping periods and for mismatched units.
* AI text containing an ungrounded number, a dose, or the word "خطير" is rejected;
  grounded text is accepted; Arabic-Indic digits are normalised before checking.
* The explanation falls back to a local template when Gemini is unconfigured and when it
  raises, each with a distinct Arabic reason.
* AI agreement keeps a field eligible for bulk confirmation; disagreement forces
  individual confirmation; **in both cases the deterministic value is the one stored**.
* An implausible AI value is discarded entirely.
* An invalid Gemini payload (unknown unit, unknown metric key) fails Pydantic validation.
* A failing cross-check leaves the deterministic result untouched (`ai_used` stays false).

## Frontend — 29 tests

Vitest + Testing Library, with the API client mocked so the real screens, routing and
state transitions are exercised.

**Navigation (4)** — exactly the four required destinations, in order; Sukkar Plus is not
a fifth tab; moving between tabs keeps the bottom bar; **ملفي stays active inside Sukkar
Plus**.

**ملفي (3)** — the patient card, الملف الصحي and التقارير والمستندات render; the سكر بلس
tile is present with its subtitle; tapping it opens the service.

**Sukkar Plus (4)** — the welcome, the main action and the journey state; all four
shortcuts; the first-use state with no fabricated metrics; and the full journey
**ملفي → سكر بلس → تقاريري → تقرير → back → back → ملفي**.

**Upload (4)** — a non-PDF and an oversized file are both rejected before any request;
success is shown **only** after the backend reports `ready` (the intermediate processing
state is asserted first); a backend failure shows its Arabic reason and a retry.

**Report detail (4)** — loading skeleton then values with their printed label and page; the
outcome, the checks and the summary source; a failed report shows its reason; a request
error shows an alert with a retry.

**Follow-up (3)** — the submit button is disabled until a reason is typed, then posts the
right payload; the shared snapshot is shown before sending; a duplicate (409) surfaces as
a clear message.

**Notifications (3)** — personal and general are separated by tab; mark-all-read calls the
backend; delete-all asks for confirmation first and only then calls the backend.

**Honest states (4)** — every appointment screen carries the prototype note; the demo
banner appears when the backend is in demo mode; **a patient session cannot render the
reviewer dashboard and never calls its endpoint**; the wellness disclaimer and sources
render.

## End-to-end (Playwright, Chromium)

Driven against the running stack at 414 × 896 (phone), 1280 × 900 and 1440 × 900 (desktop)
and 320 × 640 (narrow phone). The script performed, in one session:

sign in → الرئيسية → ملفي → tap the سكر بلس tile → upload the fixture PDF → wait for the
real `ready` status → open the report → appointment preparation → create a follow-up →
sign in as the reviewer in a separate context → start the review → record
*مراجعة مطلوبة* → return to the patient → see the simulated appointment, the four
notifications and the completed journey timeline.

Checked: **no horizontal scrolling at 320 px**, no uncaught page errors, and the desktop
canvas stays 440 px wide and centred. The only console errors were blocked Google Fonts
requests, caused by the sandbox's network policy, not by the application.

## What was **not** tested

* **Live Supabase.** No project was linked, so RLS policies, the storage bucket and the
  SQL RPCs were reviewed and written but not executed against a real Postgres. The
  equivalent authorisation rules **were** tested at the API layer (ownership isolation,
  reviewer-only routes, draft invisibility).
* **A real Gemini call.** No API key was available. The adapter, the Pydantic schema, the
  reconciliation rules and every failure path were tested with fakes and with schema
  validation; the network call itself was not made.
* **A real glucose report.** Tests use a synthetic PDF rendered in the supported layout.
  The parser was originally developed against a real Omnipod Discover report, whose values
  are not in this repository.
* **Accessibility audit.** Roles, labels, focus-visible styling, `aria-current`, dialog
  semantics and reduced-motion support are implemented and partially asserted in tests, but
  no screen-reader or automated axe audit was run.
* **Load and concurrency.** The background-task pipeline was not tested under parallel
  uploads or multiple uvicorn workers.
